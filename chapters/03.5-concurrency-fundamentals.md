# Chapter 3.5: Concurrency Fundamentals for Data Structures

## 3.5.1 Introduction

Modern software systems often need to handle multiple operations simultaneously. **Concurrency** is the ability of a program to make progress on multiple tasks at the same time, even if they don't execute simultaneously (interleaved execution). Understanding concurrency is essential when designing data structures that will be accessed by multiple threads.

### Why Concurrency Matters

- **Performance**: Utilize multiple CPU cores effectively
- **Responsiveness**: Keep UI responsive while processing data
- **Throughput**: Handle multiple requests simultaneously
- **Real-world Requirements**: Most production systems are concurrent

### ⚠️ Important Warning

> **Concurrency Is Hard**
> 
> Correct concurrent data structures are difficult to implement and reason about. In practice, engineers should prefer well-tested libraries (like `std::shared_mutex`, `std::atomic`, or thread-safe containers) unless there is a compelling reason not to. This chapter provides foundational understanding, but production code should use proven implementations.

## 3.5.2 What Is Concurrency?

### Concurrency vs Parallelism

**Concurrency**: Multiple tasks make progress by interleaving execution (can run on single or multiple cores)
```
Thread 1: [A][C][E]
Thread 2:   [B][D][F]
Time:     1  2  3  4  5  6
```

**Parallelism**: Multiple tasks execute simultaneously on different cores (subset of concurrency)
```
Core 1: [A][B][C]
Core 2: [D][E][F]
Time:  1  2  3
```

**Key Insight**: Concurrency is about **dealing with multiple things at once. Parallelism is about doing multiple things at once.**

### Interleavings

When multiple threads access shared data, their operations can **interleave** in unpredictable ways:

**Example: Two threads incrementing a counter**

```cpp
// Shared variable
int counter = 0;

// Thread 1
void thread1() {
    counter = counter + 1;  // Read, compute, write
}

// Thread 2
void thread2() {
    counter = counter + 1;
}
```

**Possible Interleavings:**

```
Interleaving 1 (correct):
Thread 1: Read(0) → Compute(1) → Write(1)
Thread 2:                          Read(1) → Compute(2) → Write(2)
Result: counter = 2 ✓

Interleaving 2 (incorrect):
Thread 1: Read(0) → Compute(1)
Thread 2: Read(0) → Compute(1)
Thread 1:              Write(1)
Thread 2:              Write(1)
Result: counter = 1 ✗ (lost update!)
```

**The Problem**: The operation `counter = counter + 1` is **not atomic**—it consists of multiple steps that can be interrupted.

## 3.5.3 Race Conditions

A **race condition** occurs when the correctness of a program depends on the relative timing of events, and the outcome varies based on the interleaving of operations.

### Example: Race Condition in Linked List

**Invariant**: "Each node's `next` pointer correctly points to the next node in the sequence."

```cpp
// Thread 1: Insert node B after A
void insertAfter(Node* A, Node* B) {
    B->next = A->next;  // Step 1
    A->next = B;        // Step 2
}

// Thread 2: Traverse list
void traverse(Node* head) {
    Node* current = head;
    while (current != nullptr) {
        process(current);
        current = current->next;  // May read inconsistent state!
    }
}
```

**Race Condition Scenario:**

```
Time | Thread 1              | Thread 2
-----|----------------------|------------------
1    | B->next = A->next    |
2    |                       | current = A
3    |                       | current = current->next (reads old A->next!)
4    | A->next = B          |
5    |                       | (misses node B!)
```

**What Breaks**: The invariant "next pointers form a valid chain" is violated during the insertion, and Thread 2 may see an inconsistent state.

### Identifying Race Conditions

Race conditions occur when:
1. **Multiple threads access shared data**
2. **At least one thread modifies the data**
3. **Operations are not properly synchronized**

## 3.5.4 Atomicity

**Atomicity** means an operation appears to execute as a single, indivisible step from the perspective of other threads. Either the operation completes entirely, or it doesn't happen at all.

### Atomic Operations

**Atomic (safe):**
```cpp
std::atomic<int> counter{0};
counter++;  // Atomic increment - cannot be interrupted
```

**Non-atomic (unsafe):**
```cpp
int counter = 0;
counter++;  // Three steps: read, increment, write - can be interrupted
```

### Compound Operations Need Protection

Most data structure operations are **compound** (multiple steps):

```cpp
// Non-atomic: Multiple steps
void push(int value) {
    if (size < capacity) {        // Step 1: Check
        data[size] = value;       // Step 2: Write
        size++;                   // Step 3: Update size
    }
}
```

**Problem**: Another thread can interleave between these steps, breaking invariants.

**Solution**: Make the entire operation atomic using synchronization primitives.

## 3.5.5 Visibility and Memory Model

### The Visibility Problem

Even if operations are atomic, threads may not see updates made by other threads due to:

1. **CPU Caches**: Each CPU core has its own cache
2. **Compiler Optimizations**: Reordering of instructions
3. **Memory Ordering**: CPU may reorder memory operations

### Example: Visibility Issue

```cpp
// Thread 1
bool ready = false;
int data = 0;

void producer() {
    data = 42;        // Write 1
    ready = true;    // Write 2
}

// Thread 2
void consumer() {
    while (!ready) {  // Read 1
        // wait
    }
    use(data);        // Read 2
}
```

**Problem**: Thread 2 might see `ready = true` but still see `data = 0` (stale value) due to:
- CPU cache not being flushed
- Compiler reordering writes
- CPU reordering memory operations

### Happens-Before Relationship

**Happens-before** is a guarantee that if operation A happens-before operation B, then:
- All memory writes by A are visible to B
- A's effects are complete before B begins

**Synchronization primitives establish happens-before relationships:**
- Mutex lock/unlock
- Atomic operations with appropriate memory ordering
- Thread creation/join

### Memory Model (Light Overview)

Modern CPUs and compilers can reorder operations for performance. The **memory model** defines what reorderings are allowed and what guarantees are provided.

**Key Concepts:**
- **Sequential Consistency**: Operations appear to execute in program order (strongest, slowest)
- **Acquire-Release**: Acquire operations see all writes before release operations
- **Relaxed**: Minimal guarantees (fastest, weakest)

**For most applications**: Use default memory ordering (acquire-release semantics) unless you have specific performance requirements.

## 3.5.6 Locks vs Lock-Free

### Lock-Based Synchronization

**Locks** (mutexes) ensure only one thread can execute a critical section at a time:

```cpp
std::mutex mtx;

void safeIncrement() {
    std::lock_guard<std::mutex> lock(mtx);  // Acquire lock
    counter++;  // Critical section
    // Lock automatically released when lock_guard goes out of scope
}
```

**Characteristics:**
- ✅ Simple to understand and use
- ✅ Prevents race conditions
- ❌ Can cause **deadlocks** (circular waiting)
- ❌ **Blocking**: Threads wait, reducing parallelism
- ❌ **Priority inversion**: High-priority thread blocked by low-priority thread

### Lock-Free (Lockless) Synchronization

**Lock-free** algorithms use atomic operations (like Compare-And-Swap) instead of locks:

```cpp
std::atomic<int> counter{0};

void lockFreeIncrement() {
    int old_value = counter.load();
    int new_value;
    do {
        new_value = old_value + 1;
    } while (!counter.compare_exchange_weak(old_value, new_value));
}
```

**Characteristics:**
- ✅ No deadlocks (no locks to deadlock on)
- ✅ Better performance under contention (no blocking)
- ❌ Much more complex to implement correctly
- ❌ **ABA problem**: Value changes A→B→A, CAS thinks nothing changed
- ❌ Harder to reason about correctness

### When to Use What

**Use Locks When:**
- Simplicity is more important than maximum performance
- Critical sections are relatively long
- You need to protect complex invariants

**Consider Lock-Free When:**
- Performance is critical
- Contention is high
- Operations are simple (increment, compare-and-swap)

**Recommendation**: Start with locks. Only consider lock-free if profiling shows locks are a bottleneck.

## 3.5.7 Deadlocks

A **deadlock** occurs when two or more threads are blocked forever, each waiting for a resource held by another.

### Classic Deadlock Example

```cpp
// Thread 1
void transfer1(Account& from, Account& to, int amount) {
    std::lock_guard<std::mutex> lock1(from.mtx);  // Lock from
    std::lock_guard<std::mutex> lock2(to.mtx);    // Lock to
    // Transfer money
}

// Thread 2
void transfer2(Account& from, Account& to, int amount) {
    std::lock_guard<std::mutex> lock1(to.mtx);    // Lock to (different order!)
    std::lock_guard<std::mutex> lock2(from.mtx);  // Lock from
    // Transfer money
}
```

**Deadlock Scenario:**
```
Thread 1: Locks from.mtx, waits for to.mtx
Thread 2: Locks to.mtx, waits for from.mtx
→ Both blocked forever!
```

### Preventing Deadlocks

1. **Lock Ordering**: Always acquire locks in the same order
2. **Timeout**: Use `try_lock` with timeout
3. **Lock Hierarchies**: Define a strict ordering of locks
4. **Avoid Nested Locks**: Minimize lock nesting when possible

## 3.5.8 Invariant-Based Reasoning for Concurrency

### The Core Principle

**Every data structure has invariants that must hold. In concurrent systems, these invariants must hold even when operations interleave.**

### Example: Stack Invariant

**Single-threaded invariant:**
- "The `top` pointer points to the most recently pushed element"
- "`size` equals the number of elements"

**Concurrent invariant:**
- "The `top` pointer points to the most recently pushed element **at all times, even during concurrent pushes**"
- "`size` equals the number of elements **even when multiple threads modify it**"

### What Breaks Under Concurrency

**Example: Stack Push Operation**

```cpp
void push(int value) {
    Node* new_node = new Node(value);
    new_node->next = top;  // Step 1: Link new node
    top = new_node;         // Step 2: Update top
    size++;                 // Step 3: Update size
}
```

**Invariant Threatened**: Between Step 1 and Step 2, the stack is in an inconsistent state:
- New node exists but isn't part of the stack yet
- `top` still points to old top
- Another thread reading `top` won't see the new node

**Solution**: Make the entire operation atomic (use a lock or lock-free technique).

### Reasoning About Concurrent Operations

**For each data structure operation, ask:**
1. What invariants must hold?
2. What intermediate states exist during the operation?
3. Can another thread observe an inconsistent state?
4. How do we prevent observation of inconsistent states?

## 3.5.9 Classic Multithreaded Data Structure Problems

These canonical problems illustrate common concurrency patterns and pitfalls. Understanding them helps reason about concurrent data structures.

### Problem 1: Producer-Consumer (Bounded Queue)

**Problem**: Multiple producers add items, multiple consumers remove items from a bounded queue.

**Invariant**: "Queue size never exceeds capacity, and `size` accurately reflects number of elements."

**What Breaks Under Concurrency:**
- **Overflow**: Multiple producers check `size < capacity`, both proceed, queue overflows
- **Underflow**: Multiple consumers check `size > 0`, both proceed, queue underflows
- **Lost Elements**: Enqueue interrupted, element never added

**Correct Solution (Lock-Based):**
```cpp
class BoundedQueue {
    std::queue<int> q;
    std::mutex mtx;
    std::condition_variable not_full, not_empty;
    size_t capacity;
    
public:
    void enqueue(int value) {
        std::unique_lock<std::mutex> lock(mtx);
        not_full.wait(lock, [this]{ return q.size() < capacity; });
        q.push(value);
        not_empty.notify_one();
    }
    
    int dequeue() {
        std::unique_lock<std::mutex> lock(mtx);
        not_empty.wait(lock, [this]{ return !q.empty(); });
        int value = q.front();
        q.pop();
        not_full.notify_one();
        return value;
    }
};
```

**Common Incorrect Approaches:**
- ❌ Busy-waiting instead of condition variables (wastes CPU)
- ❌ Checking condition without lock (race condition)
- ❌ Notifying without holding lock (missed wakeup)

### Problem 2: Readers-Writers

**Problem**: Multiple readers can read simultaneously, but writers need exclusive access.

**Invariant**: "Readers never see partial writes, writers never see concurrent modifications."

**What Breaks Under Concurrency:**
- **Read-Write Race**: Reader reads while writer writes → sees inconsistent data
- **Write-Write Race**: Two writers modify simultaneously → lost updates

**Correct Solution (Shared Mutex):**
```cpp
class ThreadSafeData {
    int data;
    std::shared_mutex mtx;  // Allows multiple readers
    
public:
    int read() {
        std::shared_lock<std::shared_mutex> lock(mtx);  // Shared lock
        return data;
    }
    
    void write(int value) {
        std::unique_lock<std::shared_mutex> lock(mtx);  // Exclusive lock
        data = value;
    }
};
```

**Common Incorrect Approaches:**
- ❌ Using regular mutex (no parallelism for readers)
- ❌ Reader checking without lock (race condition)

### Problem 3: Thread-Safe LRU Cache

**Problem**: Least Recently Used cache with concurrent access.

**Invariant**: "Most recently accessed items are at front, least recent at back. Size never exceeds capacity."

**What Breaks Under Concurrency:**
- **Cache Invalidation**: Item evicted while being accessed
- **Order Inconsistency**: Access order not properly tracked
- **Size Overflow**: Capacity exceeded due to race condition

**Correct Solution (Coarse-Grained Lock):**
```cpp
class ThreadSafeLRU {
    std::list<std::pair<int, int>> items;  // (key, value) pairs
    std::unordered_map<int, std::list<std::pair<int, int>>::iterator> map;
    std::mutex mtx;
    size_t capacity;
    
public:
    int get(int key) {
        std::lock_guard<std::mutex> lock(mtx);
        if (map.find(key) == map.end()) return -1;
        
        // Move to front (most recent)
        auto it = map[key];
        items.splice(items.begin(), items, it);
        return it->second;
    }
    
    void put(int key, int value) {
        std::lock_guard<std::mutex> lock(mtx);
        if (map.find(key) != map.end()) {
            map[key]->second = value;
            items.splice(items.begin(), items, map[key]);
            return;
        }
        
        if (items.size() >= capacity) {
            int lru_key = items.back().first;
            items.pop_back();
            map.erase(lru_key);
        }
        
        items.push_front({key, value});
        map[key] = items.begin();
    }
};
```

### Problem 4: Concurrent Counter / Rate Limiter

**Problem**: Thread-safe counter with atomic increments.

**Invariant**: "Counter value accurately reflects total number of increments across all threads."

**What Breaks Under Concurrency:**
- **Lost Updates**: Two threads increment simultaneously, one update lost

**Solutions (Showing Progression):**

**1. Single-Threaded (Baseline):**
```cpp
int counter = 0;
void increment() {
    counter++;  // Not thread-safe
}
```

**2. Coarse-Grained Lock:**
```cpp
int counter = 0;
std::mutex mtx;

void increment() {
    std::lock_guard<std::mutex> lock(mtx);
    counter++;
}
```
- ✅ Simple, correct
- ❌ Lock contention under high load

**3. Fine-Grained Lock (Per-Thread Counters):**
```cpp
std::vector<int> thread_counters(num_threads);
std::vector<std::mutex> thread_locks(num_threads);

void increment(int thread_id) {
    std::lock_guard<std::mutex> lock(thread_locks[thread_id]);
    thread_counters[thread_id]++;
}

int getTotal() {
    int total = 0;
    for (int i = 0; i < num_threads; i++) {
        std::lock_guard<std::mutex> lock(thread_locks[i]);
        total += thread_counters[i];
    }
    return total;
}
```
- ✅ Reduces contention (each thread has own counter)
- ❌ `getTotal()` requires locking all counters

**4. Lock-Free (Atomic):**
```cpp
std::atomic<int> counter{0};

void increment() {
    counter++;  // Atomic operation
}
```
- ✅ No locks, no deadlocks, high performance
- ✅ Simple for this case (atomic operations handle it)

**5. Lock-Free with CAS (For Complex Operations):**
```cpp
std::atomic<int> counter{0};

void increment() {
    int old_value = counter.load();
    int new_value;
    do {
        new_value = old_value + 1;
    } while (!counter.compare_exchange_weak(old_value, new_value));
}
```
- ✅ Lock-free, handles complex updates
- ⚠️ More complex, but shows CAS pattern

**ABA Problem (Conceptual):**
```
Initial: counter = A
Thread 1: Reads A, computes A+1
Thread 2: Changes A → B → A (value back to A)
Thread 1: CAS succeeds (thinks nothing changed, but it did!)
```
For simple counters, this isn't an issue. For pointer-based structures, it can cause bugs.

## 3.5.10 Key Takeaways

1. **Concurrency** is about interleaved execution, not necessarily parallelism
2. **Race conditions** occur when correctness depends on timing
3. **Atomicity** ensures operations appear indivisible
4. **Visibility** ensures threads see updates from other threads
5. **Locks** are simpler but can deadlock; **lock-free** is complex but avoids deadlocks
6. **Invariants** must hold even under concurrent access
7. **Prefer proven libraries** over custom concurrent implementations
8. **Classic problems** (producer-consumer, readers-writers) illustrate common patterns
9. **Lock-based → lock-free** progression shows design evolution
